# Verified platform and snapshot limits

This document records the parity limits of the Qt 6 migration and the evidence that
backs each statement. It implements the documentation required by §9 of
[`docs/superpowers/specs/2026-10-24-qt6-migration-spec.md`](superpowers/specs/2026-10-24-qt6-migration-spec.md);
the user-facing summary lives in [`README.md`](../README.md).

## How to read the evidence

Two evidence classes are kept strictly apart:

* **Automated evidence (recorded here).** Commands were run against this tree on an
  explicit `xcb` (X11) QPA path. These results say nothing about native `wayland`
  behaviour beyond what the same test binaries assert about the shared code.
* **Native Wayland live evidence (not recorded here).** Driving the real application
  on a Plasma Wayland session is the job of the live acceptance task (Task 37). No
  statement below is a passed unchecked box for that session; where native Wayland
  behaviour is described it is a specified limit, not an observation.

A missing live target gate is visibly incomplete rather than silently green.

## 1. Website iframe mode: framing denial, inline escape hatch, URL base and port

Iframe mode honours the site's `X-Frame-Options`/CSP restrictions: a site that refuses
framing is not framed. Inline mode remains the existing escape hatch, and it is the
only fallback — the refusal is not bypassed. The pre-existing inline URL-base/port
defect is corrected, so an inline article resolves relative links against the site's
real scheme/host and port instead of a mis-assembled base.

## 2. Portal shortcuts, two-key sequences and clipboard separation

Portal shortcuts accept **one** key combination, because that is the single
`XdgShortcut` combination a portal reports back. Existing two-key defaults and
multi-key sequences stay stored in the configuration unchanged and are shown as
unavailable until the user edits them; nothing is silently truncated or rewritten on
save. Labels are exactly what the portal reports — the application displays
portal-reported labels only and never invents its own.

Clipboard-change scanning (the Clipboard-mode watch on the selection buffer) and
explicit clipboard lookup remain two separate behaviours; one does not enable or
impersonate the other. Hover translation and X11 focus restoration remain X11-only,
so on Wayland both are absent by design rather than broken.

## 3. Portal dialogs, `parent_window` and best-effort activation

On Wayland the portal's `parent_window` handle is empty (the application has no X11
window id to export), so portal dialogs are created unparented. They are still modal
in intent but the compositor may place them without a transient parent.

Activation is best-effort: an activation request is a hint that a compositor may
honour or decline, and there is no mechanism here that forces it. Nothing in this
migration promises that a window becomes focused, so a declined request is expected
behaviour rather than a regression. Correspondingly, hover translation and X11 focus
restoration stay X11-only (see §2).

## 4. Print/PDF: frozen snapshot, no HTML reflow

Print preview and direct print render a frozen PDF snapshot of the article. Printer
layout metrics (paper size, margins, resolution) change the scale and render
resolution of that snapshot; they never reflow the HTML, so a print is
layout-stable with respect to the printer chosen. PDF generation is bounded by the
specified 30 s timeout and failure surfaces instead of a partial document.

## 5. Multimedia and audio

QtMultimedia internal playback and WebKit browser plugins are unavailable: the
plugin/module dependency is gone from the build, so a dictionary that relied on a
WebKit plugin gets no player from it. Remaining audio paths are the ffmpeg audio
player and external playback, with the specified audio-preference migration mapping
a stored backend onto them. In `no_ffmpeg_player` builds the stored backend text is
preserved verbatim, internal playback is hidden and external playback remains.

## 6. `HttpCachingProxy` and QNAM downloads

Chromium treats a configured `HttpCachingProxy` as an HTTP proxy, which is a
different interpretation from the one a `QNetworkAccessManager` (QNAM) applies. The
retained QNAM-based downloads therefore resolve proxy settings independently, under
the same configuration values, instead of inheriting Chromium's decision. Responses
from third-party servers keep their own headers: those headers are honoured rather
than rewritten by the cache/proxy path.

### The four gate probes

The gate itself is proven by `scripts/verify-test-gate.sh`, which runs four probes:

| probe | what it forces | expected outcome |
| --- | --- | --- |
| P1 | forced binary failure injected through the wrapper | the gate fails on the intended assertion, not on any failure |
| P2 | forced environment unavailability | the gate fails through a `RequiredEnvironment` assertion |
| P3 | clean wrapped run | the gate passes and both wrapper markers are observed |
| P4 | negative control with the run wrapper withheld | the gate fails, isolating the missing run wrapper |

These are named and characterised here by outcome; their detailed logs — including
whatever exit codes the probe runs actually produced — are produced and printed by
`scripts/verify-test-gate.sh` itself when it is executed. This document does not
restate exit codes for the probes that were not observed while writing it.

configuration, so the desktop session's dictionaries, index and history were neither
read for evidence nor modified.
